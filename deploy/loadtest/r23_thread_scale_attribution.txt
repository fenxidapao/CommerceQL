一、★ 一件我上一轮以为要新量具才能做的事：**thread 尺可以从库里直接还原**（零额度）
-----------------------------
`lg.checkpoints.checkpoint->'channel_values'->>'task_id'` 里存的就是**我们自己的 `tk_…`**，而同表 `thread_id` 就是服务端那把
`{tenant}:{user}:{session}` ⇒ **不需要新跑批、不需要改量具**，任何历史格子都能升到 thread 尺。件 = `deploy/loadtest/r23_thread_from_checkpoints.sql`（9 条语句，`ON_ERROR_STOP=1` 实跑 exit 0）。

三条前提做成了读数（不接受默认成立）：

| 尺自检 | 读数 |
|---|---|
| ① `tk → thread` 是否 1:1 | 1,370 个 `(thread, tk)` 对 / 1,370 个不同 `tk` / **跨 thread 的 tk = 0** ⇒ 映射可用 |
| ② A 档映射覆盖率 | 审计行 **95 / 95 全映射** ⇒ 落到 **77 个 thread**（而 user 只有 **12 个**）⇒ 两把尺的规模差 = 6.4 倍 |
| ③ 这些 thread 有没有窗口前的历史 | `first_in_window = 77`、`had_history = 0` ⇒ "thread 首轮"这个词在本格合法 |
| ⑧ 深度直方图 | 1 轮 ×64、2 轮 ×9、3 轮 ×3、4 轮+ ×1 ⇒ 合计 77 thread / 95 run ✓ 闭合 |

⚠️ 参数化踩到一条 psql 事实（值得进本机坑）：文件里的 `\set` **会覆盖命令行 `-v`** ⇒ 第一版"可换靶子"是假的，
我拿 U 格去覆盖时它**静默返回了 A 档的 95/77**（不是报错，是返回旧靶子的数）。改成 `\if :{?var}` 守卫后双向验过：
不给变量 ⇒ 与参数化之前**逐字相同**；给变量 ⇒ 变成 U 格的 `12 / 4 thread / 4 thread×3 轮`。
⚠️ 另一半坑：`-v upref="'u_g%'"`（值里再套单引号）会让 `:'upref'` 变成三重引号 ⇒ **0 行且零报错**。⇒ 用法注释里写明"值里不要再套引号"，并要求"覆盖生效的自检 = ② 那行必须 > 0"。
