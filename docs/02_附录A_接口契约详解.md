## A.0 通用约定

### A.0.1 基础信息

| 项 | 值 |
|---|---|
| Base URL | `https://{host}/api/v1` |
| 协议 | HTTPS（强制） |
| 编码 | UTF-8 |
| 请求体格式 | `application/json` |
| 响应格式 | `application/json`；流式端点为 `text/event-stream` |
| 时间格式 | ISO 8601（含时区偏移），如 `2026-09-14T15:30:00+08:00` |
| 金额单位 | 分（整数）或 元（字符串，两位小数）——**单接口内必须统一，响应中显式声明 `amount_unit`** |

```http
Authorization: Bearer <JWT>
```

**JWT Claims 契约（服务端必须校验）：**

| Claim | 类型 | 必填 | 说明 |
|---|---|---|---|
| `sub` | string | ✅ | 用户 ID |
| `tenant_id` | string | ✅ | 租户 ID（多租户隔离的根） |
| `role` | string | ✅ | 角色枚举，见下表 |
| `scope` | string[] | ✅ | 允许的数据域，如 `["orders","products","traffic"]` |
| `shop_ids` | string[] | ⭕ | 允许的店铺列表（空=全部） |
| `exp` / `iat` | number | ✅ | 过期/签发时间 |
| `jti` | string | ✅ | 令牌唯一 ID（用于撤销） |

**角色枚举（与 PRD §3.1 对应）：**

```

```

### A.0.6 限流

> ⚠️ **修订说明（2026-09-14）：** 原设计为"单用户 10 次/分钟"的**单一配额**，未区分端点类型。
> **这是设计缺陷** —— 它会误伤纯读取操作。反例：前端要拉**会话列表**（A.5.4）+ **会话详情**（A.5.2）+ **指标口径字典**（A.7.1）+ **认证资产**（A.7.2），光渲染一个界面就可能用掉 4~6 次配额，用户**一次查询都还没发**就可能撞限流。
> **修正：按端点类型分桶。** 查询类配额保护的是 LLM 与数据库资源；读取类只需防爬与防误用，额度应显著更宽。

| 桶 | 覆盖端点 | 单用户默认 | 单租户默认 | 超限响应 |
|---|---|---|---|---|
| **查询类** | `POST /query`、`POST /clarify` | **10 次/分钟** | 100 次/分钟 | `429` + `Retry-After: 30` |
| **读取类** | `GET /sessions`、`GET /session/{id}`、`GET /semantic/*`、`GET /query/{task_id}`、`GET /admin/eval/*` | **120 次/分钟** | 1200 次/分钟 | `429` + `Retry-After: 5` |
| **写入类** | `POST /feedback`、`POST /session`、`DELETE /session/{id}` | **30 次/分钟** | 300 次/分钟 | `429` + `Retry-After: 10` |
| **管理员类** | `POST /admin/eval/run`、`GET /admin/audit` | **5 次/分钟** | — | `429` + `Retry-After: 60` |
| **全局并发** | 全部（另计） | — | 100 并发 | `429` |

**补充规则：**

| 规则 | 说明 |
|---|---|
| 分桶独立计数 | 各桶配额独立，读取类**不占用**查询类额度 |
| 前端配合 | 前端必须**避免 N+1**：列表页只调列表端点，明细按需加载；**禁止为渲染一个列表而循环调用详情端点** |
| 缓存优先 | 读取类端点应配合前端缓存（TanStack Query）+ 服务端缓存，减少真实请求 |
| 超限响应头 | 每次请求都返回 `X-RateLimit-Bucket`，便于前端定位是哪个桶超限 |
| **⚠️ `429` 的语义边界** | **`429` 只用于"配额超限"。其他情况一律不得复用 `429`。** 特别是「同一会话已有进行中的查询」（FR-10.5 串行）→ 走 **`409` + `SESSION_CONFLICT`**（§A.11）。<br>**理由（2026-09-15 定）：** `429` 的响应契约包含 `X-RateLimit-Limit/Remaining/Reset` 三个头，而**会话串行没有"剩余额度"这个概念** —— 复用会让这些头的语义失真（前端若用它做倒计时条会显示错误信息）。这也是"**用错层的机制去补救另一个层的问题**"的典型：配额是资源治理，串行是并发状态控制，两者不同层 |

```http
X-RateLimit-Bucket: read
X-RateLimit-Limit: 120
X-RateLimit-Remaining: 118
X-RateLimit-Reset: 1789374400
```

## A.1 `POST /api/v1/query` —— 提交自然语言查询（SSE 流式）

**用途：** 核心端点。提交自然语言问题，流式返回处理进度、SQL、数据、图表与结论。

### A.1.1 请求

```json
{
  "question": "上个月华东区GMV是多少，环比怎么样",
  "session_id": "ss_01J8XABC",
  "options": {
    "max_candidates": 3,
    "allow_clarify": true,
    "chart_preference": "auto",
    "timezone": "Asia/Shanghai",
    "explain": true,
    "max_rows": 5000,
    "async_if_slow": true,
    "async_threshold_ms": 8000
  }
}
```

| 字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `question` | string | ✅ | — | 长度 1–500 |
| `session_id` | string | ⭕ | null | 传值则延续会话；不传则新建 |
| `options.max_candidates` | int | ⭕ | 3 | 候选 SQL 路数（1–5）。越大越准越贵 |
| `options.allow_clarify` | bool | ⭕ | true | 是否允许触发澄清 |
| `options.chart_preference` | enum | ⭕ | `auto` | `auto` / `line` / `bar` / `stacked_bar` / `pie` / `table` / `kpi` / `none` |
| `options.timezone` | string | ⭕ | `Asia/Shanghai` | IANA 时区 |
| `options.explain` | bool | ⭕ | true | 是否返回 SQL 与口径说明 |
| `options.max_rows` | int | ⭕ | 5000 | 上限受服务端硬上限约束（10000） |
| `options.async_if_slow` | bool | ⭕ | true | 超阈值自动转异步 |
| `options.async_threshold_ms` | int | ⭕ | 8000 | 转异步的延迟阈值 |

**响应：** `200 OK`，`Content-Type: text/event-stream`

### A.1.2 SSE 事件完整契约

> **⚠️ v1.2.1 关键修订（B-12）：** 原版本有两处会导致前端逻辑分叉的设计缺陷，已修正：
> 1. 原"异常路径事件**并终止流**"的说法**对 `degraded` 是错的**（与 §A.1.3 的转异步示例自相矛盾）
> 2. 前端不应按 **event 类型**判断流是否结束 —— 这会形成分叉分支
>
> **修正后的唯一规则：每个事件的 `data.terminal` 布尔字段决定流是否结束。** 前端只需一条 `if (data.terminal) close()`，**不需要维护事件类型白名单**。详见 §A.1.4。

**事件顺序（成功路径）：**

| # | event | 必发 | 终止流 | data 字段 |
|---|---|---|---|---|
| 1 | `ack` | ✅ | ❌ | `task_id`, `session_id` |
| 2 | `stage` | ✅ | ❌ | `stage=intent`, `elapsed_ms` |
| 3 | `stage` | ✅ | ❌ | `stage=schema_linking`, `elapsed_ms`, `candidates_count` |
| 4 | `stage` | ✅ | ❌ | `stage=plan_ready`, `elapsed_ms`, `plan_summary` |
| 5 | `stage` | ✅ | ❌ | `stage=sql_ready`, `elapsed_ms`, `sql`, `dialect`, `confidence` |
| 6 | `stage` | ✅ | ❌ | `stage=gate_passed`, `elapsed_ms`, `gate_detail` |
| 7 | `stage` | ✅ | ❌ | `stage=executing`, `elapsed_ms` |
| 8 | `data` | ✅ | ❌ | `columns`, `rows`, `row_count`, `truncated`, `amount_unit` |
| 9 | `chart` | ⭕ | ❌ | `chart_type`, `option`(ECharts option 子集) |
| 10 | `insight` | ⭕ | ❌ | `text`, `caveats[]`, `citations[]` |
| 11 | `meta` | ✅ | ❌ | `bundle_version`, `cost_cny`, `tokens`, `latency_ms`, `trace_id`, **`scope`**（见 §A.1.5） |
| 12 | `complete` | ✅ | **✅** | `terminal: true` |

**心跳：** 每 15 秒发一次 `event: heartbeat`（`terminal: false`），防反向代理超时断开。

**异常路径事件 —— 必须区分「终止」与「非终止通知」：**

| event | 终止流 | 触发 | data 字段 |
|---|---|---|---|
| `clarify` | **✅** | 意图=需澄清 / 召回歧义 / 绑定不唯一 | `clarify_id`, `question`, `options[]`, `reason`, `terminal: true` |
| `refuse` | **✅** | 无数据资产 / 越权 / PII / 开放式分析 | `reason`, `message`, `suggestions[]`, `terminal: true` |
| `error` | **✅** | 校验拒绝 / 执行失败 / 内部错误 | `code`, `message`, `detail`, `retryable`, `terminal: true` |
| **`degraded`** | **❌ 不终止** | 成本过高 / LLM 故障 / 超时 / 降级 | `reason`, `action_taken`, `terminal: false`, `partial_result?` |

> **`degraded` 为什么不是终止事件：** `degraded` 的语义是"发生了降级"，不是"这一轮结束了"。
> - **降级但查询仍成功**（如：换小模型、减少候选路数、命中缓存）→ 流继续，正常走 `data` → `meta` → `complete`
> - **降级为异步**（`action_taken=switched_to_async`）→ 后端**必须紧接着补发 `complete(terminal=true)`** 来干净收尾，前端随后去轮询 `poll_url`
>
> 两种情况都由 `terminal` 字段统一表达，前端**不需要为 `degraded` 写两套分支**。

### A.1.3 曲线救国：转异步

当 `async_if_slow=true` 且预估或实际延迟超过阈值时：

```
event: degraded
data: {"reason":"latency_exceeded","action_taken":"switched_to_async",
       "terminal":false,
       "task_id":"tk_01J8X1","poll_url":"/api/v1/query/tk_01J8X1"}

event: complete
data: {"terminal":true}
```

> **注意事件顺序：`degraded` 在前，`complete` 在后。** 这与本修订前的 A.1.2 正文（"异常事件终止流"）矛盾 —— **以本示例为准**，A.1.2 正文已同步修正。

### A.1.4 客户端流终止判定规则（**唯一规则，不允许分支**）

| 规则 | 内容 |
|---|---|
| **判定条件** | **`data.terminal === true`** → 关闭流、停止接收、标记本轮结束 |
| **不得使用** | ❌ 不得按 event 类型维护"终止事件白名单"（这是分叉来源） |
| **不得使用** | ❌ 不得依赖连接被服务端关闭来判断结束（代理/超时都会关连接） |
| **超时兜底** | 若 **90 秒**内未收到任何事件（含心跳），客户端应主动中止并提示"连接异常"，同时调 `POST /query/{task_id}/cancel` 释放服务端资源 |
| **用户中止** | 用 `AbortController` 主动断开，并调 `cancel` 端点（否则服务端继续烧 token） |
| **`terminal` 缺失时** | 视为 `false`（向后兼容），并记录告警日志 —— 契约要求每个事件的 data 都带该字段 |

**各事件 `terminal` 取值一览（便于自检，实现仍以字段为准）：**

| terminal: true（终止） | terminal: false（不终止） |
|---|---|
| `complete`、`clarify`、`refuse`、`error` | `ack`、`stage`、`data`、`chart`、`insight`、`meta`、`heartbeat`、**`degraded`** |

### A.1.5 结果范围披露策略（**B-8：空结果 vs 被权限过滤**）

> **问题（前端设计评审提出）：** 当数据库层 RLS 静默过滤掉全部行时，查询会返回 0 行。UI 面对空结果**无法区分"真的没有数据"和"有数据但被你的权限过滤了"**，用户会因此误判（"系统说上月没订单"）。
>
> **但这不是简单加个提示就能解决的** —— 直接告知"有数据但你看不到"会构成**存在性信息泄露**（用户可通过反复试探，二分出哪些数据存在）。所以必须**按隔离层级区分披露策略**。

**`meta` 事件新增字段：**

```json
"scope": {
  "level": "tenant_isolated" | "role_limited" | "unrestricted",
  "applied": true,
  "notice": "当前结果已按你的数据范围过滤" | null,
  "disclosable": true | false
}
```

**三级披露策略：**

| level | 场景 | 是否告知 | `notice` | `disclosable` | 理由 |
|---|---|---|---|---|---|
| `unrestricted` | 该用户对此数据域无任何范围限制 | 不需要 | `null` | `true` | 无过滤发生 |
| `role_limited` | **同租户内**的角色 / 类目 / 部门范围限制 | **可以给中性提示** | `"当前结果已按你的数据范围过滤"` | `true` | 用户**本就知道**自己有范围限制（`GET /semantic/assets` 只返回他可见的资产），提示不构成新增泄露 |
| `tenant_isolated` | **跨租户**隔离 | **绝不告知** | `null` | **`false`** | ⚠️ 告知即泄露**其他租户数据的存在性**。响应必须与"真的没数据"**完全不可区分** |

**三条红线（必须遵守）：**

| # | 红线 | 说明 |
|---|---|---|
| 1 | **不得通过间接量泄露** | 禁止返回"被过滤行数""过滤前后总数差""可见/不可见比例"等任何可反推出存在性的量 |
| 2 | **`truncated` 语义严格限定** | `truncated` **只表示"因 `LIMIT` 截断"**，与 RLS 过滤**无关**。RLS 过滤**不得**置 `truncated=true`（否则用户能反推"还有数据"） |
| 3 | **跨租户响应不可区分** | `tenant_isolated` 且结果为空时，响应体必须与"该租户真的没有数据"**逐字段一致**，且**不返回 `scope` 之外的任何线索**。开发期须用此场景做专项测试 |

**实现要求（给后端）：**

| 要求 | 说明 |
|---|---|
| **计划期判定，不是事后猜** | `scope.level` 必须在**查询计划阶段**由确定性代码算出（依据 JWT 的 `role` / `scope` / `shop_ids` 与语义包策略），**不得用 LLM 判断**（对应 PRD §8.4 确定性节点原则） |
| **跨租户独立测试** | 对应 PRD §13.9 红队用例集"跨租户"项 + 评测变体 V7 |
| **不进入 `insight` 文案** | ⚠️ **结论生成（LLM）不得提及"数据被过滤"**。`notice` 是**结构化的固定文案**，由前端渲染，不得由 LLM 自由生成（否则提示措辞不可控，可能描述出被过滤内容的特征） |

> **与 PRD 的对应：** 本策略落实 PRD §11.2「数据库层 RLS 是最终强制边界」与 §11.3「PII 三级防护」之间缺失的一环 —— **"边界生效之后，如何向用户解释结果"**。已同步登记为 PRD §11.7。

> **补充说明（2026-09-14 修订）：** 本端点原缺失，导致前端左栏"会话列表"无数据源，只能退化为 `localStorage` 本地维护。

## A.8 健康检查（**三个探针，职责分离**）

> **2026-09-15 修订（回应回填请求 U-06）：** 原设计只有单一 `/healthz`，把**硬依赖（数据库/Redis/语义包）与软依赖（LLM/embedding）混在同一个端点**里。这会造成两个真实故障：
> ① 编排层若用它做健康探针 → **LLM 一挂就判定实例不健康**，进而被摘流量/重启，而系统本可以降级继续服务 → **等于把已设计好的降级路径作废，变成可用性事故**；
> ② 只有一个端点 → **无法区分"进程卡死"与"依赖故障"**，runbook 判不了。
> **修正：按"谁来消费"拆成三个端点。**

### A.8.1 依赖分级（**先看这张表，其余由此推导**）

| 依赖 | 类型 | 失败时的正确行为 | 计入 readiness？ |
|---|---|---|---|
| 元数据库（含 checkpointer、`audit_log`） | **硬** | 摘流量（**不重启**）—— 无状态存储则无法保证幂等与审计 | ✅ |
| Redis（缓存 / 会话串行锁 / 限流） | **硬** | 摘流量 —— 无锁则**无法保证 FR-10.5 串行与限流**，属安全边界 | ✅ |
| 语义包已加载 | **硬** | 摘流量 —— **无口径 = 不可用**，不是降级（§5.1"越准越危险"） | ✅ |
| 对话 LLM（DeepSeek） | **软** | **降级**（模板查询 / 提示重试），继续服务 | ❌ |
| **embedding（Ollama）** | **软** | **降级**（稀疏 + Join 图扩展 + 值检索），继续服务 | ❌ |

> ⚠️ **最容易做错的一条：软依赖不得计入 readiness。** LLM 与 embedding 都已有明确的降级路径（PRD NFR-2.2 / NFR-2.7）；把它们塞进 readiness，等于**让"降级"变成"不可用"**。

### A.8.2 `GET /api/v1/healthz/live` —— liveness

**消费方：** 进程重启决策（K8s `livenessProbe` / Swarm）。

|---|---|

| 事件循环阻塞 > 5s（疑似死锁/同步阻塞调用） | `503` |

> ⚠️ **诚实说明（不是卖点，是现状）：** 当前部署为单机 Docker Compose（PRD 假设 A-7），**Compose 不会因 `unhealthy` 自动重启容器** → 本探针**当前没有自动消费者**。保留它的理由有二：① 它是迁往 K8s/Swarm 的必需项，成本仅一次路由；② 它给 runbook 一个**独立于依赖状态**的"进程是否卡死"判据。**不得声称"已实现健康自愈"。**

| 情况 | `status` | HTTP |
|---|---|---|

## A.10 图表 Spec Schema

后端返回**受约束的 ECharts option 子集**，前端仅渲染，不得自行决定图表类型。

```json
{
  "chart_type": "line",
  "version": "1.0",
  "option": {
    "title": { "text": "GMV 月度趋势" },
    "tooltip": { "trigger": "axis" },
    "legend": { "data": ["GMV"] },
    "grid": { "left": "3%", "right": "4%", "bottom": "3%", "containLabel": true },
    "xAxis": { "type": "category", "data": ["2026-05","2026-06","2026-07","2026-08"], "name": "月份" },
    "yAxis": { "type": "value", "name": "GMV（元）" },
    "series": [
      { "name": "GMV", "type": "line", "smooth": true, "data": [15200000,16400000,17800000,18234500] }
    ]
  },
  "meta": {
    "metric": "gmv",
    "unit": "CNY",
    "time_range": { "start": "2026-05-01", "end": "2026-08-31" },
    "truncated": false,
    "row_count": 4
  }
}
```

**`chart_type` 枚举与选择规则：**

| 数据形态 | chart_type | 规则 |
|---|---|---|
| 时间序列 | `line` | x 轴为时间且 ≥ 3 个点 |
| 分类对比 | `bar` | 分类维度 + 单指标 |
| 多指标分类对比 | `stacked_bar` / `grouped_bar` | 分类维度 + ≥ 2 指标 |
| 占比 | `pie` | ≤ 8 个分类，且指标语义为占比/构成 |
| 单值 | `kpi` | 结果仅 1 行 1 列 |
| 明细 | `table` | 行数 > 20 或列数 > 6 |

**约束：**
- 数值型数据必须显式转 number，禁止字符串（防 ECharts 渲染异常）
- 分类数 > 50 时必须聚合为 Top-N + 其他
- 金额类必须在 `yAxis.name` 标注单位
- **不允许后端返回任意 JS 代码或 `formatter` 函数字符串**（XSS 与注入风险）

**⚠️ `SESSION_CONFLICT`(409) 的补充约定（2026-09-15 新增，回应回填请求 U-04）：**

| 项 | 约定 |
|---|---|
| 触发 | 同一 `session_id` 已有进行中的查询 → 后端**先等待最多 3s**（覆盖"用户连点两次"的真实场景），仍未释放才返回 |
| 响应头 | `Retry-After: 3`（建议值，非硬性）。**不返回** `X-RateLimit-*` —— 这不是配额事件 |
| **不得复用 `429`** | 理由见 §A.0.6 末行（`429` 是配额语义；会话串行是**状态冲突**语义） |
| 前端处理 | 按"**稍后自动重试**"处理（建议 1 次自动重试）；**不得**进入"限流禁用"态（那是 `429` 的语义，06 §10.4） |
| 可观测 | 该码本身已与 `429` 区分 → **不需要额外的 `reason` 标签**去分辨"串行超时 vs 配额超限" |

**⚠️ `EXEC_RESOURCE_EXCEEDED`(422) 的补充约定（2026-09-15 新增，回应回填请求 U-12）：**

| 项 | 约定 |
|---|---|
| 触发 | **执行期**资源上限被突破（P0 默认：单查询内存 > **512MB**，FR-6.4）。**与 gate3 无关** —— 该查询**已通过**成本闸门并**开始执行** |
| `detail.limit_type` | **只用于区分"维度"**，取值：`memory`（P0）/ `rows` / `temp_disk`（P1 预留）。⚠️ **不得**用它去区分"是否成本闸门"—— 那是**码**的职责 |
| **与 `COST_TOO_HIGH` 的区别（易混点，必须分对）** | ① `COST_TOO_HIGH` = **预执行**（gate3 EXPLAIN 估算超预算）→ **一行都没跑**，`cost_ledger` 无执行成本 ② 本码 = **执行期中止** → **可能已产生部分成本**，须如实记账。**用户动作相同（收窄范围），但状态与记账不同** → **不得合并为一个码** |
| **与行数截断的区别（易混点）** | **行数超限不报错** —— 走**截断 + 完整标记**（FR-6.7、`meta.truncated`）。本码只用于**不可截断的资源**（内存：无法"截断一半"后仍返回正确结果） |
| 响应头 | **不返回** `X-RateLimit-*`（非配额事件） |
| 前端处理 | 与 `COST_TOO_HIGH` 一致：**提示收窄范围**；`⭕` 表示"**需改变请求后**才可重试"（原样重试必然再次失败） |
| 可观测 | `cost_ledger` 须记录中止时的**已消耗资源**（与 `EXEC_TIMEOUT` 同一处理路径） |

**⚠️ 与 `refuse` 事件的区分（易混点）：** 「查询成功但结果为空」**不是错误码，也不使用 `refuse` 事件** —— 它走正常的 `data` + `complete` 路径，由 `meta.scope` 表达范围信息（见 §A.1.5、PRD §11.7）。`FORBIDDEN_SCOPE` 表达的是**资产级**拒绝，不是行级过滤。

## A.13 超时与流式约定

| 项 | 值 | 说明 |
|---|---|---|
| 普通请求超时 | 60s | — |
| SSE 连接最长 | 5 分钟 | 超时后客户端应改用异步轮询 |
| SSE 心跳间隔 | 15s | 防代理断开 |
| 澄清有效期 | 5 分钟 | 过期返回 `CLARIFY_EXPIRED` |
| 异步结果保留 | 1 小时 | 之后返回 404 |

**反向代理配置要求（部署时必须满足）：**

```nginx
proxy_buffering off;              # 必须关闭，否则 SSE 被缓冲
proxy_cache off;
proxy_read_timeout 300s;
proxy_set_header Connection '';
chunked_transfer_encoding on;
```

> **这是 SSE 落地最常见的坑：** Nginx 默认 `proxy_buffering on` 会把 SSE 事件攒起来一次性发送，导致前端看不到流式进度。

## A.14 前端集成注意事项（写给实现者）

| # | 事项 | 说明 |
|---|---|---|
| 1 | **不要用原生 `EventSource`** | 它不支持 POST body 与自定义 Header。查询必须 POST（含问题、会话、权限上下文）。用 `fetch` + `ReadableStream` 手写 SSE 解析，或 `@microsoft/fetch-event-source` |
| 2 | SSE 解析要处理跨 chunk 的半行 | 一个事件可能被拆到多个网络分片，必须缓冲到遇到 `\n\n` 再解析 |
| 3 | 必须处理 `heartbeat` | 否则心跳事件会被当成未知事件报错 |
| 4 | 流结束判定 | 收到 `complete`/`refuse`/`clarify`/`error` 之一即为终止事件 |
| 5 | 用户主动中止 | 用 `AbortController`，并调 `cancel` 端点（避免服务端继续烧 token） |
| 6 | 图表更新 | 收到 `chart` 事件后再渲染 ECharts，避免空实例 |
| 7 | SQL 展示 | 收到 `sql_ready` 就展示，不必等 `data`（透明度建立信任） |
| 8 | 口径展示 | `insight.caveats` 必须展示，不可折叠隐藏（PRD FR-8.2） |
| 9 | 截断提示 | `data.truncated=true` 必须显式提示"这是前 N 行"（PRD FR-6.7） |
| 10 | trace_id | 展示在错误提示中，便于用户反馈 |
