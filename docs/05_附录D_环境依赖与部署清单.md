## D.1 版本矩阵

### D.1.1 运行时与基础设施

| 类别 | 依赖 | **要求版本** | 为什么是这个版本 | 不满足的后果 |
|---|---|---|---|---|
| 语言运行时 | **Python** | **3.12+** | 用户已定；`LangGraph` / `SQLAlchemy 2.x` / `pydantic v2` 均在 3.12 上稳定 | 3.11 及以下可能在依赖解析时出现 `EBADENGINE` 类告警；部分库不再提供 3.11 轮子 |
| 语言运行时 | **Node.js** | **20 LTS 或 22 LTS** | Vite 要求 ≥ 18；**必须选 LTS**，非 LTS 版本 6 个月后失维护 | 非 LTS 会在半年内被迫升级，且部分依赖不提供对应预编译包 |
| 包管理（前端） | npm / pnpm | npm ≥ 10（随 Node 20+）或 **pnpm ≥ 9** | pnpm 更快且磁盘友好；若团队无偏好用 npm 亦可 | — |

#### D.1.3.1 磁盘容量**必须分盘核算**（实测依据）

> **⚠️ 原写法（v1.1）是"磁盘 ≥ 25GB 可用"，这是错的** —— 它**未区分盘符**，且把 `bge-m3` 的 1.2GB 算进了**并不存放它的盘**。单一数字无法指导容量规划。

**实测环境（2026-09-15）：**

| 盘 | 总量 | 已用 | 可用 | 使用率 | 本项目占用 |
|---|---|---|---|---|---|
| **C:** | 274 GB | 215 GB | **59 GB** | **79%** ⚠️ | 仅 Docker Desktop 应用本体 ≈ **30MB** |
| **D:** | 191 GB | 114 GB | **77 GB** | 60% | Ollama 模型 **18GB** |
| **E:** | 954 GB | 540 GB | **415 GB** | 57% | **Docker 数据 15GB** + 项目文件 |

**结论与硬性要求：**

| # | 要求 |
|---|---|
| 1 | **本项目不向 C 盘写入任何数据。** C 盘实测已用 **79%**，是本机最紧张的盘，**不得作为任何数据落盘位置** |
| 2 | **新机器部署时，下列两项必须作为前置步骤显式设置**（两者默认位置**都在 C 盘**）：<br>① **Docker Desktop → Settings → Resources → Advanced → Disk image location** → 指向非 C 盘（本机为 `E:\DockerData\DockerDesktopWSL`）<br>② **`OLLAMA_MODELS`** → 指向非 C 盘（本机为 `D:\ollama_models`，见 §D.1.4） |
| 3 | **本机已完成上述两项优化，不得在部署脚本或后续文档中"改回去"**（已实测确认，见 §D.1.4） |

> **⚠️ 关于 `wsl.exe` 的一个实测约束（会影响部署形态选择）：** 本机**安全策略曾拦截 `wsl.exe` 调用** → 依赖 WSL 内部命名的自动化脚本不可靠。**影响：** 涉及"在 WSL 内进容器执行命令"的脚本不要写成部署前置步骤。**缓解：** 统一用 `docker compose exec` / `docker compose run`（走 Docker Desktop 的 API，不依赖直接调用 `wsl.exe`）。

### D.1.4 Ollama（embedding）专项约束

**为什么这一节必须单独存在：** embedding 是本项目**第二个模型依赖**，而它的部署形态与 DeepSeek（公网 API）**完全不同** —— 它在**宿主机**上，而应用跑在**容器**里。**这是本项目最容易在"本地能跑、换台机器就挂"的地方。**

| 项 | 约束 |
|---|---|
| 安装形态 | **宿主机原生安装**（非容器）—— 本项目采用此形态，因为已有 GPU 直通与已装模型 |
| 默认监听 | `127.0.0.1:11434` —— ⚠️ **容器内写这个地址必然连不上**（容器有自己的 loopback） |
| **必须拉取的模型** | **`bge-m3`**（1024 维，约 **1.2GB**，一次性下载）<br>`ollama pull bge-m3` |
| **模型落盘位置**（✅ **已配置，无需额外操作**） | 用户级环境变量 **`OLLAMA_MODELS` = `D:\ollama_models`** 已设置 → `ollama pull` 的 blob **直接落 D 盘，不占 C 盘**（该目录当前 **18GB**，含 5 个既有模型：`llama3.1` / `medexpert` / `nomic-embed-text` / `qwen2.5` / `qwen2.5vl`）。<br>⚠️ **不要**为"避免占用 C 盘"而**重设**该变量 —— 指向新目录会使**既有模型全部不可见**（需全部重新拉取），属无谓返工。**本机已是最优状态**（见 §D.1.3.1） |
| 端口状态 | 默认**端口不一定常开** —— Ollama CLI 调用时按需启动服务。⚠️ **首请求会因模型加载产生额外延迟**，必须计入性能预算；**健康检查须容忍"未预热"状态**（不得因首次探测未响应就判定故障） |
| 显存预算 | 实测 RTX 4060 Laptop **8188 MiB**，`bge-m3` 常驻约 **1.2–1.5GB** → 与 DeepSeek 无冲突（那是公网 API，不占本机显存），但与**本机其他大模型互斥** |
| **降级方案** | 若拒绝下载 1.2GB → 复用已装的 `nomic-embed-text`（768 维）。**必须**同步：① 配置与文档标注"**中文稠密检索降级**" ② 上调稀疏权重 + 扩充附录 B 同义词表 ③ 写入评测报告作为**已知能力缺口**。**不得静默切换** |

**访问方式对照（记住这一张表就够）：**

| 后端运行位置 | `EMBEDDING_BASE_URL` | 是否可用 |
|---|---|---|
| **宿主进程**（uvicorn 本地跑，**开发期推荐形态**） | `http://127.0.0.1:11434` | ✅ **无障碍**（见 §D.6.1 步骤 3） |
| **容器**（类生产形态） | `http://host.docker.internal:11434` | ⚠️ **需同时满足两个条件**，见 §D.5 |

> **⚠️ 安全说明（必须显式记录）：** 让容器访问宿主 Ollama，需要在 Ollama 侧放宽绑定（`OLLAMA_HOST=0.0.0.0` 或等效）。**这是安全面变化** —— 该绑定**仅允许对本机/内网开放，绝不暴露公网**。放宽绑定的事实必须写进部署记录，不得默认打开。

## D.5 Docker Compose 配置要点

```yaml
# deploy/docker-compose.yml（配置契约，含注释说明每个决策）
services:
  web:
    build: ../frontend
    ports: ["80:80"]                 # 唯一对外暴露的端口
    depends_on: [api]
    # 只托管静态文件 + 反代，不含任何业务逻辑

  api:
    build: ../backend
    expose: ["8000"]                 # ⚠️ expose 而非 ports —— 不暴露宿主，减少攻击面
    env_file: [.env]
    extra_hosts:
      - "host.docker.internal:host-gateway"   # ⚠️ 访问【宿主 Ollama】必需（D.1.4）
                                              #    Docker Desktop 默认已解析该名；Linux 宿主必须显式声明
    volumes:
      - ../semantic:/semantic:ro     # 语义包只读挂载（运行时不可改）
      - sandbox:/data/sandbox        # SQLite 评测沙箱
    depends_on:
      pg: {condition: service_healthy}
      redis: {condition: service_started}
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/api/v1/healthz/ready"]
      # ⚠️ 必须用 /ready 而不是 /healthz：
      #    /healthz 含【软依赖】(LLM/embedding)，会把"可降级继续服务"误判为不健康
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 60s              # 覆盖 Ollama 未预热时的首次模型加载延迟（见 D.1.4）

  worker:
    build: ../backend
    command: ["python", "-m", "app.worker"]   # 异步长查询
    env_file: [.env]
    depends_on: [redis, pg]

  pg:
    image: pgvector/pgvector:pg16    # ⚠️ 用带 pgvector 的镜像，不要用官方 postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./init:/docker-entrypoint-initdb.d:ro   # 初始化 RLS 策略 +【两个角色】app_rw / app_ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app_rw"]
      interval: 10s
    # ⚠️ P0（单机 Compose）：元数据与分析【共用本实例】，靠 app_ro 角色级只读强制
    #    代价：分析查询与业务写入共享资源 → "不影响线上交易"这条收益 P0 拿不到（PRD §8.5 说明）
    #    升级路径：加 replica 服务（流复制）→ 只把 ANALYTICS_DB_URL 改指副本 → 配置级改动

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--maxmemory", "512mb", "--maxmemory-policy", "allkeys-lru"]
    volumes: [redisdata:/data]

volumes:
  pgdata:
  redisdata:
  sandbox:
```

**7 个关键点：**

| # | 点 | 理由 |
|---|---|---|
| 1 | **`pgvector/pgvector:pg16` 而不是 `postgres:16`** | 官方镜像不含 pgvector 扩展，启动时会报 `extension "vector" does not exist` |
| 2 | **`api` 用 `expose` 不用 `ports`** | 后端不经 Nginx 直连会绕过限流与安全响应头 |
| 3 | **语义包只读挂载（`:ro`）** | 运行时不可改，防"发布流程被绕过" |
| 4 | **`init/` 挂载到 `docker-entrypoint-initdb.d`** | **RLS 策略、`app_rw` / `app_ro` 两个角色、列级 GRANT 必须在初始化时建立**，否则新环境缺安全边界 |
| 5 | **`healthcheck` 用 `/healthz/ready`（不是 `/healthz`）** | `/healthz` 含**软依赖**（LLM/embedding）→ 用它会让"可降级继续服务"被判为不健康（附录 A §A.8.1）。`/ready` 只含硬依赖 |
| 6 | **`extra_hosts: host.docker.internal:host-gateway`** | 容器内的 **API 要访问宿主 Ollama**（D.1.4）。不声明则 `host.docker.internal` 不可解析 |
| 7 | **`start_period: 60s`** | 首次启动时 Ollama 可能未预热（模型加载），需给足启动宽限，避免误判 unhealthy |

> **⚠️ Ollama 不是 Compose 服务（重要，容易配错）：** 它**运行在宿主机**，不在本 compose 文件里。因此：
> - 必须**先确保宿主 Ollama 已启动、且已 `ollama pull bge-m3`**，再起容器（§D.6.1）
> - 容器**不能**通过 `depends_on` 等待它 —— 它是**软依赖**，未就绪时应降级而非阻塞启动
> - 若宿主 Ollama 绑的是 `127.0.0.1`，容器**永远连不上** → 需放宽绑定（`OLLAMA_HOST=0.0.0.0` 或等效），**且仅对本机/内网开放**

## D.6 环境搭建步骤（可执行清单）

### D.6.1 首次搭建

| # | 步骤 | 验证方式 |
|---|---|---|
| 1 | 安装 Python 3.12+ | `python --version` |
| 2 | 安装 Node 20/22 LTS | `node --version` |
| 3 | 安装 Docker Desktop，**必须选 WSL 2 backend**，**并把 Disk image location 指向非 C 盘**（本机为 `E:\DockerData\DockerDesktopWSL`，见 §D.1.3.1），确认 Compose v2 | `docker compose version`；且配置中 disk image location **不在 C 盘** |
| 4 | **确认宿主已安装 Ollama**（若未装则先装），**并确认 `OLLAMA_MODELS` 指向非 C 盘**（本机已配为 `D:\ollama_models`，**无需更改，切勿重设**） | `ollama --version`；`ollama list` 能列出模型 |
| 5 | **拉取 embedding 模型（本项目唯一新增下载项）** | `ollama pull bge-m3`（约 1.2GB，一次性）→ `ollama list` 应含 `bge-m3` |
| 6 | 克隆仓库，复制 `.env.example` → `.env`，填入 `DEEPSEEK_API_KEY` | `grep -c "sk-" .env` 应为 1 |
| 7 | 确认 `.env` 已在 `.gitignore` | `git check-ignore .env` 应有输出 |
| 8 | `cd backend && python -m venv .venv && .venv/bin/pip install -r requirements.txt`<br>⚠️ `jieba` 必须在 **venv 内**装（宿主 Anaconda 那份不可复用） | `pip list \| grep -E "fastapi\|jieba"` |
| 9 | `cd frontend && npm install` | `npm ls react` |
| 10 | `docker compose -f deploy/docker-compose.yml up -d pg redis` | `docker compose ps` 两个服务 healthy |
| 11 | 执行数据库迁移（**含 RLS 策略 + `app_rw` / `app_ro` 两个角色**） | `alembic upgrade head` 无报错 |
| 12 | 灌入合成数据集（附录 C） | `SELECT count(*) FROM v_order_paid;` 返回预期行数 |
| 13 | **验证 RLS 生效** | 用租户 A 身份查询，结果不应含租户 B 数据 |
| 14 | **验证 embedding 后端连通**（按后端运行形态二选一） | ① 后端**本地运行**：`curl http://127.0.0.1:11434/api/tags`<br>② 后端**容器化**：`docker compose exec api curl -s http://host.docker.internal:11434/api/tags` → 必须返回模型列表。**失败即说明 `host.docker.internal` 或 `OLLAMA_HOST` 没配对** |
| 15 | 后端起服务 | `curl localhost:8000/api/v1/healthz` → `status: ok`；`curl localhost:8000/api/v1/healthz/ready` → `200` |
| 16 | 前端起 dev server | 浏览器能打开页面且能发一次问答 |
| 17 | **验证 SSE 未被缓冲** | 提交查询，**SQL 应在 2–3 秒内先出现**，而不是等 8 秒一次性全出 |

> **⚠️ 步骤 4–5 的顺序不能调：** Ollama 未启动或未拉取 `bge-m3` 时，系统仍能启动（它是**软依赖**，走降级），但**稠密检索不可用 → schema linking 质量显著下降**。若在步骤 15 看到 `degraded_dependencies` 含 `embedding`，说明这两步没做全。

### D.6.2 部署上线检查清单（**验证式，不是"点过就算"**）

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 危险 SQL 拦截 | 提交"删除订单表"→ 返回 `GATE_AST_REJECTED` |
| 2 | 跨租户隔离 | 用租户 A 身份无法查到租户 B 数据（含缓存层与检索层） |
| 3 | PII 屏蔽 | 客服角色查询结果中手机号显示为掩码 |
| 4 | `SELECT *` 拦截 | 提交"把所有字段给我"→ 被拒 |
| 5 | 成本闸门 | 构造大范围查询 → 返回 `COST_TOO_HIGH` 并给建议 |
| 6 | **SSE 端到端** | 生产域名下 SQL 仍先于数据到达（证明 Nginx 未缓冲） |
| 7 | SPA 刷新 | 在 `/session/xxx` 直接刷新页面不 404 |
| 8 | CORS 关闭 | 生产环境跨域请求应被拒（证明未开 `*`） |
| 9 | 后端端口未暴露 | 从外部无法直连 `:8000` |
| 10 | 密钥未泄漏 | 静态产物中 `grep -r "sk-"` 无命中 |
| 11 | 审计可用 | 完成一次查询后审计表有完整记录 |
| 12 | 熔断可用 | 触发预算熔断后查询被拦并提示 |
| **13** | **embedding 降级路径** | **停掉宿主 Ollama** → 查询仍返回结果，且 `meta` 标注"降级检索"、`/healthz` 的 `degraded_dependencies` 含 `embedding`，而 **`/healthz/ready` 仍为 `200`**（若变 503 说明**软依赖被错计入 readiness**，附录 A §A.8.1） |
| **14** | **审计 fail-closed** | 故障注入（审计 sink 抛错）→ **不下发 `data` 事件**，返回 `INTERNAL` + `trace_id`（NFR-2.6） |
| **15** | **会话串行冲突** | 同一 `session_id` 并发双发 → 第二个等待 3s 后返回 **`409` + `SESSION_CONFLICT`**（**不是 `429`**） |
| **16** | **liveness 不含外部依赖** | 停掉 PG → `/healthz/live` **仍为 `200`**（不应触发重启），而 `/healthz/ready` 为 `503` |
| **17** | **只读边界可断言** | 用 `ANALYTICS_DB_URL` 尝试 `CREATE TABLE` / `INSERT` → **必须被 PG 拒绝**（角色级 `default_transaction_read_only`） |
| **18** | **分词两侧同源** | 同一文本在写入路径与查询路径产出**同一个 `tsvector`**（PRD §12.8 硬约束 1） |

## D.7 版本升级策略与兼容性风险

| 依赖 | 升级风险 | 策略 |
|---|---|---|
| **Ollama / `bge-m3`** | **中高** —— 换模型或换维度会**使全部向量索引失效**；Ollama 自身版本升级也可能改变输出 | **`EMBEDDING_MODEL` / `EMBEDDING_DIM` 必须配置化并参与索引 DDL**；换模型走"**版本递增 + 重建索引**"流程，**不改代码**；升级后跑中文召回测试。⚠️ **锁死 Ollama 版本**，不要自动升级 |
| **`jieba`** | **中** —— **词典或分词算法变化会使写入侧与查询侧的 `tsvector` 不一致** → 召回静默断裂 | 固定精确版本；**升级后必须重建全部 `tsvector` 列**并重跑分词一致性测试；电商自定义词表随语义包版本化 |
| **DeepSeek 模型 ID** | **高** —— `deepseek-chat` / `deepseek-reasoner` 已退役；未来 `deepseek-v4-pro` 也可能变更（官方公告仅承诺"计费方式不变"） | **模型 ID 必须配置化**（`LLM_MODEL_FAST` / `LLM_MODEL_STRONG`），不硬编码；上线前检查官方文档的模型列表 |
| **pgvector** | 中 —— 索引类型与参数随版本演进 | 升级前在沙箱验证 HNSW 参数；不跨大版本跳升 |
| **PostgreSQL** | 中 —— 大版本升级需 `pg_upgrade` | 不跨大版本直接升级；RLS 策略需在升级后复查 |
| **LangGraph** | **高** —— 该库迭代快，checkpointer API 曾多次变更 | 固定精确版本；升级必须重跑完整评测；`checkpointer` 表结构变更需迁移脚本 |
| **LangChain 系** | 高 —— 同上 | 尽量少依赖 `langchain` 上层封装，只用 `langchain-core` + `langgraph` |
| **Ant Design** | 中 —— 大版本有破坏性变更 | 固定在 5.x 内升级；大版本升降需全面回归 UI |
| **ECharts** | 低 | 5.x 内升级；chart spec 契约版本号同步评估 |
| **Vite / React** | 中 —— React 19 有较大变更 | P0 固定在 React 18；升级另立任务 |
| **Nginx** | 低 | 跟随稳定版；升级后**必须重验 SSE**（缓冲行为是历史踩坑点） |

**通用原则：**

| 原则 | 说明 |
|---|---|
| **锁定精确版本** | 生产用 lock 文件，不用范围约束 |
| **升级走独立任务** | 不与功能变更混在同一次提交 |
| **升级必须重跑评测** | 尤其当变更涉及 prompt / LLM SDK / LangGraph 时（PRD §13.5） |
| **保留回滚能力** | 镜像按 Git tag 构建，可一键回退上一版本 |
| **模型变更需 A/B** | 换模型等于换系统行为，必须冻结评测集对照（PRD §13.3） |

## D.8 已知环境层面的风险

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| E-1 | **Windows 上开发、Linux 上部署的差异**（路径分隔符、换行符、`uvloop` 仅 Linux 可用） | 本地能跑线上报错 | 开发期即用 Docker 跑后端；`.gitattributes` 强制 `LF`；不依赖 `uvloop` 特有行为 |
| E-2 | **Docker Desktop 在 Windows 的资源占用与文件挂载性能** | 挂载卷读写慢，数据集灌入耗时长 | 数据卷用命名卷而非 bind mount；大批量灌数用容器内脚本而非宿主→容器逐条写 |
| E-3 | **DeepSeek API 并发上限**（flash 2500 / v4-pro 500，账号级） | 高并发时报 429 | 并发信号量 + 指数退避；必要时申请扩容（官方免费） |
| E-4 | **API Key 泄漏**（本项目开发期已实际发生一次） | 费用被盗刷 | 环境变量 + `.gitignore` + 日志过滤 + 定期轮换（PRD §11.5） |
| E-5 | **pgvector 扩展缺失**（用了官方 `postgres` 镜像） | 启动报 `extension "vector" does not exist` | 用 `pgvector/pgvector:pg16` 镜像 |
| E-6 | **RLS 策略未随迁移创建** | 新环境缺安全边界，可能跨租户泄漏 | RLS 策略纳入 Alembic 迁移；部署检查清单第 2 项强制验证 |
| E-7 | **Nginx 默认缓冲** | SSE 表现为"等 8 秒一次性出结果" | `proxy_buffering off` + 部署检查清单第 6 项 |
| E-8 | **Node 非 LTS 版本失维护** | 半年后被迫升级 | 固定 20/22 LTS |
| E-9 | **CORS 误配 `*`** | 安全缺陷 | 生产关闭 CORS；检查清单第 8 项 |
| E-10 | **`VITE_*` 变量被编译进静态产物** | 误放密钥 = 公开泄露 | 红线：`VITE_*` 只放非敏感配置 |
| **E-11** | **容器内访问不到宿主 Ollama**（最常见：后端容器化后 `EMBEDDING_BASE_URL` 仍写 `127.0.0.1`；或 Ollama 仍绑 `127.0.0.1`） | **embedding 全部失败 → 稠密检索不可用**，schema linking 质量显著下降 | ① 容器用 `host.docker.internal` + `extra_hosts`（§D.5）② 宿主 `OLLAMA_HOST=0.0.0.0`（**仅本机/内网**）③ **开发期直接用"后端本地运行"形态绕过该问题**（§D.1.4 对照表） |
| **E-12** | **Ollama 未启动 / 未拉取 `bge-m3` / 未预热** | 服务能起（软依赖），但**静默降级**；首请求因模型加载而延迟抖动 | `ollama list` 校验模型存在；`EMBEDDING_TIMEOUT_SECONDS=30` 覆盖冷启动；healthcheck `start_period: 60s`；**`meta` 必须显式标注降级，不得静默**（NFR-2.7） |
| **E-13** | **显存不足** —— `bge-m3`（约 1.2–1.5GB）与 `qwen2.5vl:7b` 等本地大模型**同时常驻**会挤爆 8GB | Ollama 请求失败或系统级卡顿 | **不要同时常驻**；Ollama 会按需加载/卸载，但首次并发会抖动；必要时错开使用 |
| **E-14** | **审计存储故障导致 fail-closed**（服务主动拒绝下发结果，NFR-2.6） | **服务实际不可用**，且这是**主动设计选择**（非 bug） | runbook 明确"审计库故障"处置；`audit_log` 与业务元数据**同库**；告警 **P0**；**该缺口必须写入评测报告，不得静默**（R-17） |
| **E-15** | **把 P0 的只读边界表述为"已实现读写分离/只读副本"** | 被追问即失分；且与文档自身矛盾 | 严格表述为"**同实例 + `app_ro` 角色级只读强制**"；升级为真副本才可称读写分离（PRD §8.5 红线） |
| **E-16** | **数据落盘在 C 盘**（Docker disk image location 或 `OLLAMA_MODELS` 用了默认值 —— **两者的默认值都在 C 盘**） | 本机 C 盘实测**已用 79%（仅剩 59GB）**，是三盘中**最紧张**的；向其写入会直接加剧紧张 | **C 盘只放 Docker Desktop 应用本体**（≈30MB）。新机器部署时**前置设置** Disk image location（→ E 盘）与 `OLLAMA_MODELS`（→ D 盘）。**本机已优化到位，不要改回去**（§D.1.3.1） |
