## 三、不达标成因（按证据强弱排）

1. **并发超过有效容量**。c50 档 `admitted` 只有 10 条、790 条被限流 429；c50 / pool14 的 `error_frame 69` 与 `LLM_SEMAPHORE_FLASH=8` 一致 —— 50 并发远高于可承诺容量。
2. **准入达标的两档 P95 仍远超 8s**。c50_pool14 `p95 = 26579.3`（约 3.3 倍门限）、c8 `p95 = 14137.3`（约 1.8 倍）。
3. **c8 档的分母不可用**。该档 `outcomes` 只有 `error_frame` 与 4xx/5xx，`ok` 键缺席；回执自带 caveat 明写「本场景 0 条真正完成 ⇒ P95 的分母全是失败/降级样本，不可判达标」。即使数字低于 c50_pool14，也不能读成「降并发达标」。
4. **request_cap 截断**。c50 档 `request_cap 800` 与 `requests 800` 相等、`wall_s 21.104`，采样窗口被 cap 提前结束，不是稳态读数。

## 四、已知偏差（照实登记，不改回执）

1. 台账此前转述「`p95 36012.2`、`n = 31`」与回执现读两处都对不上：`36012.2` 是 **p99**，`samples` 是 **100**。属抄录错位。
2. `p95_scope` 三件均标 `admitted_http_2xx`，而 c8 档 `ok` 键缺席 ⇒ 「分母为 http 2xx 准入样本」这一标注与实测自相矛盾。
3. `g6_p95_le_8s` 同一字段出现三种形态（`null` / `False` / `True` 潜在），汇总时必须先分档、不能直接聚合。
4. 回执 `git_dirty`：c8 那份为 `true`（另两份 `false`），即当轮工作树有未提交改动。

## 五、结论与后续

- G-6 状态：**未达标 / `UNVERIFIED`**。三档均不满足 `P95 ≤ 8s`，其中 c50 档连 `admitted ≥ 20` 也不满足。
- 缺的不是读数而是容量决策：要么继续降并发阶梯（`U-126` 的 c=8 已测，仍不过门；更低档需重新起服务与计费），要么书面豁免 8s 门（改判据须先取号）。
- 本报告不重算 P95、不改配置、不引旧回执以外的数据。
