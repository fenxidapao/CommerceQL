## 二、四条阻塞（每条都是实测，不是推测）

| # | 阻塞 | 取证命令与读数 |
|---|---|---|
| 1 | 在跑的 `commerceql-api-1` 是 **W4 收口之前的陈旧镜像**，没有 `query` 路由 | `docker exec commerceql-api-1 grep -n include_router /srv/app/main.py` → 只有第 239 行 `health.router` 一条；`ls /srv/app/api/routers/` → 只有 `__init__.py`、`health.py`；带自签令牌 `POST /api/v1/query` → `404 {"detail":"Not Found"}` |
| 2 | **pgbouncer 未运行**（不是没配） | `docker ps` → `commerceql-api-1 / redis-1 / pg-1` 三个，无 pgbouncer 容器；但 `deploy/docker-compose.yml:75` 有完整的 `pgbouncer` 服务（`POOL_MODE=transaction`、`DEFAULT_POOL_SIZE=30`，正是断言③的口径）⇒ 起它即可，但**未获授权**。⚠️ 顺带发现：该服务用 `image: edoburu/pgbouncer:latest`，是全 compose **唯一未固定版本**的镜像（其余 5 个都带 tag）⇒ 起哪天的行为不可复现 |
| 3 | 走通 `POST /query` 必花**真实 DeepSeek 额度** | `app/core/config.py:70-72`，`DEEPSEEK_BASE_URL` 默认生产地址、模型为 `deepseek-flash`/`deepseek-v4-pro`；授权范围是"只跑不烧额度子集" |
| 4 | 本地模型替代路线**同时**卡在 embedding 维度与信号量上 | Ollama 可达（`qwen2.5:7b`、`llama3.1:8b`、`nomic-embed-text`），但 `EMBEDDING_MODEL=bge-m3` 不在列表，`nomic-embed-text` 768 维 ≠ `EMBEDDING_DIM=1024` ⇒ 启动校验第 3 行会 FAIL；且 `LLM_SEMAPHORE_FLASH=8 / _PRO=2` 下 50 并发主要在排队，宿主 CPU 的 7B 延迟既不代表生产也不代表降级 ⇒ **主动放弃**该路线，不用它出 G-6 数字 |

阻塞 1 是硬阻塞：解开它 = `docker compose build api && up -d api` = **重启 W6 正在用的栈**。

⚠️ 另有一条环境事实压在上面：本机 `docker images` 里**没有** `edoburu/pgbouncer`、`nginx`、`grafana/grafana`
三个镜像（实测只有 `redis:7-alpine`、`pgvector/pgvector:pg16`、`prom/prometheus:v2.54.1`）
⇒ 断言③、反代 `404` 的活体验证、Grafana 看板的真实渲染，都还需要**联网拉镜像**。
本窗口未尝试拉取：拉镜像会改变共享宿主状态，且不在授权范围内。

| 四场景跑批 | — | **未执行**（§二） |

自检的价值不在"它绿了"，在于**它能在量具坏掉时红**：变异 ① 在第一次实现时**漏判**，
根因是 `httpx.ASGITransport` 会把响应体整体攒好再交回（`_transports/asgi.py:158-185`），
TTFB 恒等于端到端时间，于是"只测第一帧"这种致命错误在自检里看不出来。
改成起在真 TCP 环回端口上之后才被抓到 —— 这段已写进 `driver.py` 与 loadtest README §六。

## 四、给 W6 的 G-6 输入口径

1. **现在能引用的**：只有"压测仪器可用 + 四场景参数与回执 schema 已定"。
   回执 schema = `w7.loadtest.receipt/1`，字段 `latency_ms.{p50,p95,p99,max,mean}`、`ttfb_ms`、
   `outcomes{}`、`codes{}`、`g6_p95_le_8s`、`g6_caveat`。**W6 门禁表里 G-6 请填 UNVERIFIED（外部阻塞），
   不要填空、更不要填通过。**
2. **不能引用的**：任何"§16.5 已通过"、"连接池在负载下正确"、"pgbouncer ≤30"。前者的前提（新路由的栈）不存在，
   后者连进程都没有。
3. **`async_if_slow` 陷阱**（拿到授权后第一次跑批的人必须知道）：默认 `true` + `async_threshold_ms=8000`
   会把超过 8s 的查询转异步并**正常终止该流** ⇒ 直接看 `total_ms` 的 P95 会天然贴近 8s 而"达标"。
   判 G-6 必须 `--no-async`，或按 `task_id` 轮询补完真实完成时间。
   且 `Outcome.SWITCHED_TO_ASYNC` 目前全仓**无消费方** ⇒ 帧上区分不了真完成与转异步（已进 RELAY 给 W4）。
4. **取数时点**：真实压测与 W6 评测**不得同时跑**（同机 CPU 与同一 pg 连接池）。谁先跑由主流程定，
   另一方在报告里写明避让。
